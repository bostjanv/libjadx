# External-classpath recovery feasibility (Phase 7)

## Decision and scope

**PARTIAL internal feasibility; public adoption BLOCKED.** This is a bounded
real-Jadx probe, not a dependency-path configuration feature. No endpoint,
production adapter, dependency, native project field or public capability changes.
An additional ordinary input JAR is explicitly a negative boundary control: its
classes become project `ClassNode`s, not external declarations.

The owned Java sources are generated by
`JadxExternalClasspathProbeTest` in a JUnit temporary directory. `app.Child`
extends `dep.Parent`; the dependency declares asymmetric overloads
`choose(int):long` and `choose(double):float`. The child overrides both and
adds `choose(long):int`, which is not an override. A separately compiled
`dep.Missing` appears in a return signature but is omitted from **both** runtime
JARs. No third-party fixture or framework archive is needed.

## Exact upstream audit

All paths below are relative to Jadx **1.5.6**, revision
[`28ff15e4ae69950aebea110a13e5ab895d234dfc`](https://github.com/skylot/jadx/tree/28ff15e4ae69950aebea110a13e5ab895d234dfc):

* `jadx-core/src/main/java/jadx/api/JadxArgs.java`: ordinary inputs and the
  `loadJadxClsSetFile` boolean; no ordinary external dependency-JAR path setting.
* `jadx-core/src/main/java/jadx/api/JadxDecompiler.java`: `load()` initializes
  the root classpath before prepare passes and subsequent lazy decompilation.
* `jadx-core/src/main/java/jadx/core/dex/nodes/RootNode.java`:
  `initClassPath()` loads the bundled set, adds application classes and builds
  caches. No external-set append hook is exposed here.
* `jadx-core/src/main/java/jadx/core/clsp/ClspGraph.java`:
  `addClasspath(ClsSet)` only initializes an empty graph; a second call throws
  `Classpath already loaded`. Its declaration map is private.
* `jadx-core/src/main/java/jadx/core/clsp/ClsSet.java` (not `ClspSet`): bundled
  `/clst/core.jcst`, format version 5; `loadFrom(RootNode)` and `save(Path)`;
  stream deserialization is **private**. Conversion excludes private,
  synthetic and bridge methods, and is not a complete editable code model.
* `jadx-core/src/main/java/jadx/core/clsp/ClspClassSource.java`: conversion
  accepts only recognized framework basenames (`android.jar`, `android.car.jar`,
  `org.apache.http.legacy.jar`); an arbitrary dependency basename is APP and
  conversion rejects it. The probe proves rejection, then packages its owned
  dependency as `android.jar` solely to exercise this internal representation.
  The resulting CORE label is artificial, **not recovered dependency provenance**.
* `jadx-cli/src/main/java/jadx/cli/clst/ConvertToClsSet.java`: upstream framework
  set preparation utility, not an ordinary library configuration option.
* `jadx-core/src/main/java/jadx/api/plugins/pass/types/JadxPreparePass.java`:
  a root-aware analysis hook, not an external-classpath path API.
* `jadx-commons/jadx-analysis/src/main/java/jadx/analysis/callgraph/`:
  `JadxCallGraph.java` and `CallGraphBuilder.java` consume existing analysis;
  `resolvedOnly` filters graph output rather than supplying dependencies.

Downloaded source audit copies and run logs are local review artifacts under
`.amp/in/artifacts/external-classpath-feasibility/` (not shipped source files).

## Experimental mechanism and observables

Preparation uses a **separate** Jadx instance whose only input contains the owned
dependency and an owned minimal `java.lang.Object` declaration. The serializer
requires a closed type universe: an initial parent-only conversion failed with
a null dereference while writing the missing Object reference. The tiny Object
stub is compiled with `--release 8`, not copied from a JDK; the two overloads use
primitives so no further framework stubs are needed. It serializes a `.jcst`;
the application instance never receives
that JAR as an input. The test deliberately bridges two private APIs:
`ClsSet.load(InputStream)` and `ClspGraph.nameMap`. It loads the converted set
against the application root, adds only absent names to the existing bundled
map (preserving the real bundled Object instead of installing the stub), then
rebuilds hierarchy caches. A custom `JadxPreparePass`, ordered before
`OverrideMethodVisitor`, installs it before override analysis. An initial
after-load installation did not recover override markers, exposing the ordering
requirement. This is not a
supported plugin/configuration path and must not be promoted into production
by copying this reflection helper.

Assertions compare independent absent/recovered application instances:

* absent parent: no override attribute or `DONT_RENAME` marker for either
  overridden signature;
* supplied internal set: matching external `ClspMethod` override declarations
  and `DONT_RENAME` markers for both signatures immediately after preparation;
* after requesting Java source, the external graph declaration remains known
  and outside the project census, but the raw method's `DONT_RENAME` marker is
  no longer present. The test preserves this lifecycle counterexample: these
  raw attributes are not a durable public rename guard;
* the asymmetric non-override remains unmarked; the omitted class remains
  unknown to the graph and absent from the root;
* application enumeration remains exactly `app.Child`, with no resolvable
  parent project `ClassNode`, while the external declaration is graph-known;
* ordinary additional-input control enumerates two project classes and resolves
  the parent as an APP class, demonstrating why that is not external recovery;
* missing converted file, bad header, and an ordinary JAR supplied to the
  converted-set loader fail before map installation; the application remains
  in its absent-dependency state.

These are resolution/override-analysis observations, not proof of complete
instruction xrefs, arbitrary transitive dependency closure, field metadata,
generic hierarchies, hostile class-set parsing, safe collisions or concurrent
classpath mutation. The ordered prepare pass proves this fixture, not safe
ordering for every analysis/plugin or a general dependency refresh mechanism.

## Verification

Final command (the XML copy was also performed while holding the same lock):

```sh
flock .amp/in/implementation-gradle.lock ./gradlew test \
  --tests dev.libjadx.probes.JadxExternalClasspathProbeTest \
  --tests dev.libjadx.probes.JadxRelatedMethodProbeTest.missingParentHasNoCompletenessOrDontRenameMarker \
  --tests dev.libjadx.jadxadapter.InputCensusTest \
  --tests dev.libjadx.probes.RawInputCensusProbeTest --no-build-cache
```

**27 tests passed, 0 failed, 0 skipped:** 2 new probes, 1 missing-parent
regression, 23 input-census cases and 1 raw-census regression. Local evidence:
`final.log` and `final-xml/` in the artifact directory. A focused intermediate
run also passed both new tests. Earlier development runs each reported
27 tests / 1 failure: missing serializer closure, late installation, and an
incorrect expectation that preparation markers persist after source generation.
These failures informed the boundaries above rather than being hidden.
The first invocation stalled in Gradle's cache-lock owner ping before tests;
its hung process was stopped after repeated unchanged checks, then the command
was rerun once the stale owner was gone. Logs and a thread dump are retained.

## Persistence and smallest follow-on

The prepared set and all JARs are test-owned temporary artifacts. No application
save occurs; no dependency configuration survives restart, is added to native
`.jadx`, or has been GUI-round-trip qualified. No release requalification claim.

The smallest follow-on is a reviewed design decision on whether a pinned
internal adapter is acceptable at all, or upstream support is required. Before
any contract/configuration slice, prove pre-analysis installation preserving
the bundled framework set, arbitrary-library provenance without filename
spoofing, collision/transitive closure rules, immutable ownership and startup
failure semantics. Allowed-root/admission policy and portable export ownership
would then need their own bounded proof. Do not advertise an ordinary JAR
external-classpath option on the evidence here.

# ADR 0001: Strict mapping export and import; defer local/propagated renames

Status: export and bounded import safety decisions implemented; scoped parameter subset implemented; local/propagated follow-ups deferred after PR #17 safe-replay feasibility, 2026-09-29.

Phase 5.2 requires native mapping export, parameter/local renames and
related-method propagation only where pinned Jadx and the matching GUI prove
the behavior. Declaration editing and strict Tiny v2 export are separate slices.

The pinned
[`MappingExporter`](https://github.com/skylot/jadx/blob/28ff15e4ae69950aebea110a13e5ab895d234dfc/jadx-plugins/jadx-rename-mappings/src/main/java/jadx/plugins/mappings/save/MappingExporter.java)
does export a `JadxCodeData` with a selected mapping format. Its implementation
deletes an existing single-file output before writing and catches/logs its own
exceptions instead of reporting success or omissions to a caller. That is
insufficient for this service's explicit path safety, external conflict and
truthful success contract. Existing `/project/settings` only attaches an
already existing mapping; it is not an import or export transaction.

The safe export uses mapping-io 0.8.0 directly, validates the accepted baseline
file as well as the loaded tree, combines observed native alias precedence and
additive LINE comments, and reparses owned bytes before publishing. A destination
must be new; same-directory hard-link creation provides atomic no-clobber
behavior, exercised against an existing owned name on the actual filesystem.
`ATOMIC_MOVE` is excluded because it may replace an existing destination.
Unsupported namespaces/options, unknown/duplicate records, unresolved keys,
native code refs and non-LINE styles fail closed. No partial mapping is offered.
Directory identities and path components are rechecked; the residual final
syscall race with directory replacement is documented, rather than claimed
to be eliminated. This is an operational output, never project persistence.
See [the export probes and gates](../phase-5-mapping-export.md).

PR #13 proves original semantic parameter positions through `MethodNode`,
`MethodGen`, `CodeRenameVisitor`, real-Jadx fixtures and matching-GUI resave.
Parameter edits now use `MTH_ARG` keys with mandatory source snapshot and
session/revision admission. Unsupported signature forms fail closed and the
collision policy conservatively treats all declared method variables as
potentially overlapping. See [scoped evidence](../phase-5-scoped-editing.md).

`forVar` remains insufficient as a public stable identity. The owned optimized
fixture changes a merged local's emitted SSA metadata under SIMPLE; FALLBACK
emits no declarations. Native keys are not bound to their originating settings
in `.jadx`. We do not expose a persistent local subset without a broader
settings/GUI retargeting proof. Existing native VAR renames on a parameter's
method are conservatively rejected as ambiguous rather than translated.
`JavaMethod.getOverrideRelatedMethods()` provides candidates, not a proof of
complete propagation. Local and propagation operations still return
`UNSUPPORTED_CAPABILITY`. This is a capability boundary, not a new persistence
format or architectural departure.

Follow-up work should use owned optimized-variable and inheritance fixtures,
verify native keys and matching-GUI resave, and design mapping output with
allowed-root, symlink, conflict, omission and failure behavior before adding
new routes. Mapping import now uses its own admitted transaction: captured strict Tiny bytes
are resolved against original full keys and the current engine/native/attached
state, the entire conservative merge is staged privately, and only one native
replacement can publish it. Matching effective values are no-ops; differing
aliases/comments conflict. The narrow attached prefix plus one native LINE
suffix is proved by real-Jadx and matching-GUI fixtures. No source path is
attached and no file is saved. Arbitrary composites and inner-class renames
remain unsupported; automatic engine aliases count as existing effective values.
This deliberately bounded subset avoids lossy Tiny-to-native reconstruction.
See [import evidence](../phase-5-mapping-import.md). Neither mapping operation
imports or exports scoped or propagated native edits. Codec output is
generated by mapping-io, never hand-formatted Tiny text.

## PR #14 completeness decision

Status: propagation feasibility completed with negative evidence; explicit
propagation stays unsupported. A fully resolved Joined implements two interface
branches, but pinned OverrideMethodVisitor returns after an already processed
ancestor and omits SeparateRight.joined(I)I. The omitted method has no ambiguity
or DONT_RENAME marker. Missing parent and collapsed original-input probes show
additional gaps. One original-key seed record also fails hot/fresh alias agreement.
See [executable evidence and native/GUI diagnostics](../phase-5-related-propagation.md).

Do not replace exact related groups with candidate lists. The smallest compatible
follow-up is a bounded original-input census and independent hierarchy verifier,
followed by all-owner conflicts, group-private staging and actual propagated
service/GUI persistence gates. No architecture, native format or dependency
change is approved or needed by this evidence-only slice. Locals remain deferred.

## PR #15 independent verification prerequisite

Status: bounded original-input census and independent completeness verifier
implemented for the documented class/JAR/DEX subset. The owned independent
interface family has four seed-independent original declarations, and comparison
detects the pinned candidate omission. Strict individual pinned input readers
avoid bulk loader exception swallowing and retain every duplicate definition.
Configured origins remain internal; public SymbolRef provenance is unchanged.

The verifier rejects bridge/synthetic and covariant families pending a separate
editability/native/GUI proof. Missing/external/duplicate branches, parse failures
and exhausted limits never expose a complete group. java.lang.Object is an
explicitly modeled terminal only for signatures absent from its pinned classpath
method table; its own method signatures remain external and unverifiable.
No inheritance branch is inferred from generated source.

This fits the existing architecture and adds no persistence format. Existing
input dependencies gain compile visibility without an upgrade. Propagation stays
UNSUPPORTED until PR #16 proves group admission, collision/staging/failure
semantics and actual propagated service/native/restart/GUI behavior. See
[the exact subset and evidence](../phase-5-hierarchy-verifier.md).

## PR #16 replay safety decision

Status: outcome B; explicit propagation remains unsupported. PR #15 resolved
independent completeness for the conservative subset, but that does not resolve
native replay. Real service batches containing every verified original member
record rename the requested family and persist those records. After generated
owner unload/replay, however, two unrelated CovariantLeaf aliases become
`m0value`; fresh native reopen restores `value`. The read-only generated control
does not show that change. This fails the required unchanged-nonmember and
hot/fresh gates even for the retained four-member Joined family.

Retain existing presence-based 422 rejection, UNSUPPORTED capability, accepted
schema and legacy behavior. Preserve the executable counterexample and separate
actual GUI Save As diagnostic. Do not persist automatic suffixes or add unrelated
native records to force agreement. The smallest next slice is safe engine replay
feasibility before a group transaction can be admitted. No architecture or
Phase 6 exit decision is made. See [replay evidence](../phase-5-propagated-edits.md)
and [validation](../pr-16-review.md).

## PR #17 replay preservation boundary

Status: outcome B; the production edit path and unsupported propagation boundary
are retained. Fresh replacement is preferable for independent mutable engine
state and passes the owned Joined bridge and complete native-state probes.
However, an ordinary supported rename of `ReturnClash.value()I` removes a
return-only collision: a fresh engine changes untouched `value()String` from
`m0value` to `value`, while the current path preserves `m0value`. The existing
unchanged-overload regression failed in the provisional replacement path.

Under PR #17's explicit unchanged-nonmember constraint, neither keeping old
aliases nor recomputing them is an admissible generic solution. The provisional
production implementation was removed. Manually setting aliases, adding unrelated
native records or relaxing the assertion would weaken that constraint. A future
replacement implementation therefore needs human approval specifically for
consistent automatic-alias recomputation, or a different strategy that proves
both invariants. Cost acceptance alone is insufficient. No such design change
is adopted here. See [counterexamples and measurements](../phase-5-safe-replay.md).
